## 2. Package Manager

**pnpm 10.34.1.** No package manager was previously selected in this repository (it contained only
`docs/` at the start of Phase 1), so pnpm was chosen per the fixed decision to prefer pnpm when nothing
else has been established. `packageManager: "pnpm@10.34.1"` is pinned in `package.json`, and
`pnpm-lock.yaml` is the single lockfile in the repository — no `package-lock.json` or `yarn.lock` exists
or should be introduced.

## 3. Node Version

**Runtime target: Node 20.19.0**, declared in `.nvmrc` and as `"engines": { "node": ">=20.9.0" }` in
`package.json` (Next.js 16.3.1's own documented minimum).

This is the actual Node version installed in the development environment this phase was built in, and
all verification (install, lint, typecheck, test, build) was run against it successfully. See
**Known Limitations** below for an important caveat: as of this phase's authoring date, Node 20.x is
past its official LTS support window, and this is documented rather than silently ignored.

## 4. Next.js Configuration

- App Router (`src/app/`), TypeScript, Turbopack build (Next 16's default; no `--webpack` flag was
  added).
- `next.config.ts` is intentionally minimal — no experimental flags, no custom webpack/Turbopack
  configuration, no image domains, no redirects. Nothing in Phase 1 requires configuration beyond the
  framework defaults.
- Middleware is **not** used. Next.js 16 deprecated and renamed the `middleware.ts` file convention to
  `proxy.ts` (confirmed directly from the Next.js 16.3.1 documentation bundled in
  `node_modules/next/dist/docs/`, not from prior training knowledge, since a Next.js major version this
  new can differ from what any model was trained on — see `AGENTS.md` / `CLAUDE.md` at the repository
  root, which Next.js itself generates as a live warning about exactly this). No `proxy.ts` exists yet
  either — it is explicitly Phase 2 work (session refresh), per `03-supabase-foundation.md` §7.

## 5. TypeScript Configuration

`tsconfig.json` is the file generated by `create-next-app` for this Next.js version, unmodified beyond
what Next.js itself manages:

- `"strict": true` — TypeScript strict mode is on.
- `"moduleResolution": "bundler"`, `"module": "esnext"`, `"jsx": "react-jsx"`.
- Path alias: `"@/*": ["./src/*"]`.
- `include` covers `**/*.ts`, `**/*.tsx`, and `**/*.mts` (the latter needed for `vitest.config.mts` —
  see §7), plus Next's own generated route-type files under `.next/types/`.

No additional strict flags (e.g. `noUncheckedIndexedAccess`) were layered on top. The framework default
strict mode is treated as sufficient for Phase 1's scope; revisiting stricter compiler flags is left to
a later phase if a concrete need appears, rather than adding rules pre-emptively that make day-to-day
development harder without a demonstrated benefit.

Only directories with real, meaningful content were created, per the explicit instruction not to create
empty folders for appearance:

  phase-1/             (this phase's documentation)

`src/components/` and `src/types/` were **not** created in Phase 1. There is no genuinely reusable
presentational component yet (the foundation page is a single, self-contained page — extracting
components now would be premature abstraction), and there is no real shared/generated type to put in
`src/types/` (database types cannot be generated without a linked project or local schema — see
`03-supabase-foundation.md` §9; fabricating placeholder types was explicitly disallowed). Both
directories are documented here as intentional, deferred, not omitted by oversight.

Defined in `package.json`:

| ----------------- | ---------------------------------------------------------------------- | -------------------------------------------------------- |
| `dev`             | `next dev`                                                             | Local development server                                 |
| `build`           | `next build`                                                           | Production build                                         |

| `check`           | `pnpm format:check && pnpm lint && pnpm typecheck && pnpm test`        | Combined non-destructive quality gate                    |

`check` intentionally does not run `build` — it is the fast, everyday feedback loop (format, lint,
types, tests). `pnpm build` is run as its own explicit step locally and in CI, matching the CI job's
own step-by-step structure (see `04-quality-and-ci.md`).

The `db:types:*` scripts are prepared but not yet run against anything — see `03-supabase-foundation.md`
§9 for why, and §7 for the reasoning behind Node's `vitest.config.mts` file extension.

## 8. Key Engineering Decisions

- **Scaffold in a temp directory, then merge.** `create-next-app` refuses to run in a non-empty
  directory, and `docs/` already existed. The app was scaffolded into an isolated temp directory,
  every file was verified byte-for-byte against the source before merging, and the temp directory was
  removed only after that verification succeeded. `docs/phase-0/` was never touched.
- **Respect `create-next-app`'s own dependency choices over "latest".** The scaffold pinned
  `eslint@^9` and `typescript@^5` even though `eslint@10` and `typescript@7` exist on npm. The
  Next.js team's own scaffolding tool is a stronger compatibility signal for "current stable, mutually
  compatible" than picking the newest major of each package independently, so those choices were kept
  rather than force-upgraded.
- **Downgraded `jsdom` from 30.x to 29.x.** `jsdom@30` pulls in `undici@8`, which crashed on this
  environment's Node 20.19.0 with `TypeError: webidl.util.markAsUncloneable is not a function` — every
  jsdom-environment test failed to even start. `jsdom@29` (which depends on `undici@^7`) does not hit
  this and all tests pass. This is recorded as a real, verified compatibility constraint, not a
  guess — see `05-dependency-baseline.md` for detail.
- **Removed `next/font/google` (Geist).** The default scaffold self-hosts Google's Geist font, which
  requires a network fetch at build/dev time. Since Phase 1 makes no final design-system decision and
  explicitly avoids external dependencies where avoidable, the layout uses a plain system-font stack
  instead (`system-ui, -apple-system, "Segoe UI", Roboto, Helvetica, Arial, sans-serif`). This also
  makes the production build fully network-independent (verified: build succeeds with zero environment
  variables set and no network activity required).
- **`vitest.config.mts` instead of `.ts`.** Vite's native config loader warned that `vitest.config.ts`
  was being loaded as CommonJS despite using ESM `import` syntax. Rather than changing the whole
  project's module type via `package.json`'s `"type": "module"` (a much larger blast radius), the
  config file itself was renamed to the explicit-ESM `.mts` extension, which `tsconfig.json` already
  includes and Vitest already resolves.
- **Vite's native `resolve.tsconfigPaths` instead of the `vite-tsconfig-paths` plugin.** Vitest's
  bundled Vite version supports first-party tsconfig path resolution, which removed a dependency and a
  deprecation warning without any behaviour change.
- **`server-only` mocked in its own test, not worked around.** The `server-only` package is a
  conditional-exports marker (it resolves to a no-op only under Next's own `react-server` build
  condition; otherwise it always throws) — not a `typeof window` runtime check, as first assumed. The
  fix is the standard one: `vi.mock("server-only", () => ({}))` in the one test file that imports the
  server Supabase client, which is also what proves the guard exists and is wired correctly.
- **`AGENTS.md` / `CLAUDE.md` kept, not discarded as scaffold noise.** Next.js 16 auto-generates these
  files (re-written by `next dev` itself) to warn that this Next.js version may differ from a model's
  training data and to point at the bundled docs. That warning is genuinely useful and low-cost to keep,
  and directly informed several decisions in this phase (the `proxy.ts` rename, the async `cookies()`
  API, the current `createBrowserClient`/`createServerClient` patterns).

## 9. Alternatives Considered

- **npm or Yarn instead of pnpm** — rejected only because no package manager was pre-selected and the
  fixed decision explicitly prefers pnpm in that case; no functional objection to either alternative.
- **Keeping `jsdom@30`** — rejected because it does not run at all in this environment's Node version;
  reconsider once the development machine's Node runtime is upgraded (see Known Limitations).
- **`happy-dom` instead of `jsdom`** — considered as a lighter-weight alternative when the jsdom crash
  first appeared, but the root cause (an `undici` major-version incompatibility) was identified and
  fixed by pinning `jsdom@29` instead, so switching DOM implementations was unnecessary.
- **A single monolithic `eslint.config.mjs` with hand-written rules instead of `eslint-config-next`** —
  rejected; the Next.js team's own config already includes Core Web Vitals rules, TypeScript rules, and
  `eslint-plugin-jsx-a11y` for accessibility, which is more complete and better-maintained than a
  hand-rolled equivalent for a project at this stage.

## 10. Known Limitations

- **Node 20.x LTS currency.** Per the published Node.js release schedule, Node 20 entered Maintenance
  LTS in October 2024 and reached end-of-life around April 2026. This phase's documentation was authored
  in August 2026, meaning the installed runtime (20.19.0) is past its official support window, even
  though Next.js 16.3.1 itself only requires `>=20.9.0` and every command in this phase ran correctly on
  it. No Node version manager (nvm/volta) was available in this environment to switch versions safely,
  and installing one was judged out of Phase 1's scope (a development-machine change, not a repository
  change). Upgrading to an active LTS line (22.x or 24.x) is recommended before any production use.
- **No `src/components/` or `src/types/` yet** — intentional, see §6.
- **No database types** — intentional, see `03-supabase-foundation.md` §9; will be generated once a
  real schema exists (Phase 3+).
- **No live Supabase connectivity was verified** — no project credentials were provided in this
  session; see `03-supabase-foundation.md` §8.
